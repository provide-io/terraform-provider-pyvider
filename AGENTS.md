# AGENTS.md

Guidance for coding agents working in this repository.

## What this is

`terraform-provider-pyvider` is the official Pyvider provider: a Python
Terraform/OpenTofu provider built with [Pyvider](https://github.com/provide-io/pyvider)
that publishes the components in
[pyvider-components](https://github.com/provide-io/pyvider-components) and ships
as a single Flavorpack executable (`.psp`).

- Provider name: `pyvider` (`[tool.pyvider] name` in `pyproject.toml`).
- Components: `component_packages = ["pyvider.components"]`, from the
  `pyvider-components` dependency. This repository holds no component code.
- Version: the `VERSION` file (`pyproject.toml` reads it dynamically).
- Dependency floors and the reasons for each are commented in
  `pyproject.toml`; read them before changing a floor.

## Layout

| Path | Contents |
|---|---|
| `examples/` | Terraform examples per component kind; also the corpus pyvider's Terraform Gate runs with `soup stir --recursive`. Every directory here must `init` against this provider. |
| `tests/conformance/` | Drives a packaged provider binary over tfplugin6. Skipped unless a binary exists; `PYVIDER_CONFORMANCE_REQUIRED=1` turns a missing binary into a failure. |
| `tests/e2e/` | OpenTofu 1.13.0-rc1 provider-linting end-to-end test (needs `PYVIDER_CONFORMANCE_PSP` and `PYVIDER_OPENTOFU_BINARY`). |
| `tests/proof/` | Contracts for the provider-linting proof (manifest, casts, docs). |
| `tests/test_*.py` | Release, staging, installer, and build contracts. |
| `ci/` | Every script the workflows run. Workflow `run:` blocks call these rather than holding inline logic. |
| `docs/` | Registry documentation generated by plating (`make docs` → `ci/build-docs.sh`). |
| `plating/` | Guides and partials plating injects into `docs/`. |
| `provider-linting-*.cast`, `provider-linting-proof.json` | The committed linting proof: three films (OpenTofu, direct, walkthrough) and their schema-v3 manifest. |

The Part 7 provider-linting tutorial lives in
[pyvider-tutorial](https://github.com/provide-io/pyvider-tutorial), not here.

## Setup and checks

```bash
uv sync                         # dev environment in .venv
uv run ruff format . && uv run ruff check .
uv run mypy .
uv run pytest -p no:xdist       # CI runs one process; run it that way before pushing
```

`wrknv` tasks mirror these (`we run lint`, `we run format`, `we run typecheck`,
`we run test`). Pre-commit runs detect-private-key, ruff, codespell, mypy, and
bandit on each commit.

The CI gate (`.github/workflows/ci.yml`) is ci-tooling's reusable
`python-ci.yml`: lint, typecheck, tests, security audit (fails on any
unwaived advisory), and secret scan. `build-provider.yml` also runs on every
push and PR: it builds all five platforms and runs conformance against each.

## Building and running locally

```bash
make build                      # flavor pack → dist/terraform-provider-pyvider.psp and dist/<platform>/terraform-provider-pyvider_v<VERSION>
make test-conformance           # build, extract the work environment, run tests/conformance
make test-examples              # build, install, then soup stir every example
make install                    # install into ~/.terraform.d/plugins/local/providers/pyvider/<version>/<platform>/
make docs                       # regenerate docs/ with plating
```

Use a local build from Terraform with:

```hcl
terraform {
  required_providers {
    pyvider = {
      source  = "local/providers/pyvider"
      version = "<VERSION>"
    }
  }
}
```

A rebuilt package with an unchanged version needs `make clean-workenv` before it
will launch (Flavorpack keys the extracted environment on the package
checksum). The first launch unpacks the runtime; `make warm-workenv` does that
ahead of anything with a handshake timeout.

Platforms built and released: `linux_amd64`, `linux_arm64`, `darwin_amd64`,
`darwin_arm64`, `windows_amd64`. There is no `windows_arm64` build (grpcio
publishes no wheel for it).

## Releasing

A release publishes exactly the artifacts of one successful
`build-provider.yml` run whose head SHA is the release commit. Nothing is
rebuilt at release time, and nothing is attached by hand.

1. Merge the release PR with `VERSION` set to the new version.
2. Point a branch at the merge commit, then dispatch the proof build on it:
   ```bash
   git push gh-origin <merge-sha>:refs/heads/codex/release-v<VERSION>
   gh workflow run build-provider.yml --ref codex/release-v<VERSION> -f provider_linting_proof=true
   ```
   Wait for that run to succeed and confirm its head SHA is the merge commit.
3. Dispatch the release with that run's numeric ID:
   ```bash
   make release BUILD_RUN_ID=<run-id> RELEASE_REF=codex/release-v<VERSION>
   ```
   `release.yml` validates the run, stages its artifacts
   (`ci/stage-release-assets.sh`), signs the SHA256SUMS, publishes the GitHub
   release at the validated SHA (`ci/publish-release.sh`), then
   `verify-release-proof` re-downloads the release and re-runs the
   `linux_amd64` proof against the published bytes.
4. If the release job fails before publishing, fix forward and repeat from
   step 2 on the new merge commit; a build run is bound to one SHA.

The remote is `gh-origin`.

## Conventions

- No hand-edited proof artifacts. `provider-linting-proof.json` and the casts
  come from `ci/record-provider-linting.sh` in a `build-provider.yml` run with
  `provider_linting_proof=true`; commit that run's artifact.
- Workflow `run:` blocks longer than three lines belong in `ci/`, and every
  workflow step carries a comment saying what it does.
- Keep URLs and ports out of code; put them in a defaults location.
- Working plans and specs belong in `.provide/` (git-ignored), not in the
  repository.
